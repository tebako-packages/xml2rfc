# What & why

Two coupled changes, one PR — plus one deliberate de-scope.

**1. Shard-model runtime staging.** The python runtime factory's `v0.2.0` line publishes per-leg: per-package manifest shards (`<stem>.manifest.json`), per-asset `.sha256` sidecars, and OpenPGP `.asc` signatures. The monolithic `manifest.json` / `SHA256SUMS.txt` are **no longer release assets**, so the previous `tools/stage_runtime` release channel 404s against v0.2.0. The release channel is adapted to the shard model (the metanorma spawned-mirror pattern):

- Shards are enumerated with `gh release view --json assets` and selected per host on the pin's exact version plus variant suffixes.
- The shard is fetched **first** and names every other asset (the exe/image/dll spellings are read from it, never composed) — this keeps the windows three-artifact shape (`.exe` + `.dll` + `.tfs`) suffix-clean for when that leg lands.
- Every staged byte is verified three ways: `.sha256` sidecar ↔ staged bytes ↔ the shard's own digest fields, plus the identity assertions (tebako_version / platform / stem recomposition; python line = the pin exactly or a pin-suffixed variant). The `.abi` sidecar `tools/build` consumes is flowed from the shard's own `abi` key.
- The trimmed `manifest.json` and `SHA256SUMS.txt` are **derived consumer-side** into the mirror: a partial mirror never advertises bytes it doesn't carry.
- The `run-artifacts` channel is unchanged, `HOST_IDS` override kept, `die` everywhere.

**2. Version bumps.** `recipe.yml`: `upstream.version` 3.34.0 → 3.34.1 (PyPI-verified: current, classifiers cover Python 3.14, `requires_python >= 3.10`), `build.runtime` 3.13.15/0.1.3/v0.1.3 → 3.14.7/0.2.0/v0.2.0, and the ABI-line references move to `~> 3.14.0` / cp314 (recipe, `manifests/payload.yaml` ×2, `tools/gen_closure` — the wheel tag is now derived from the pin, never a literal). The committed macOS closure lock is regenerated for 3.34.1/cp314 with the staged runtime's own pip; the other legs generate in-leg on CI as before.

**3. De-scope: the windows-ucrt leg waits on the factory.** This branch originally carried a `x86_64-windows-ucrt` leg; five CI iterations proved it cannot land yet, for two factory-side reasons:

- **No mount tier on windows.** The windows python runtime's fs TU answers **any** mount with a named exit 69 (the factory README's documented windows boundary) — the exe runs only bare/dev mode. A windows payload cannot execute on its own platform until the factory lands the mount tier. Shipping a leg that cannot run is worse than not shipping it.
- **A mingw socket defect in the source factory's windows-msys build.** Bare-booted against an extracted+reshaped image tree, pip's HTTPS dies with `WinError 10035` (a non-blocking connect never waited on): upstream `_PyIsSelectable_fd` is `_MSC_VER`-guarded, so the mingw-ucrt build's Winsock handle fails the POSIX `fd < FD_SETSIZE` check. Blocking sockets work; any timeout-carrying connect does not.

Both fixes belong to the factories, not to this feedstock — tracked as tamatebako/tebako-runtime-python#23 (the mount tier) and tamatebako/python#25 (the socket guard). The **line choice already anticipates the leg**: python 3.14.7 is the one line every leg will ride, because the factory's windows-ucrt64 runtime exists only on the 3.14 line — so when the mount tier lands, the leg is a recipe row + matrix entry, not an ABI migration. `tools/stage_runtime` keeps the generic windows-aware handling (suffix/dll/`install_as`) it grew during the exploration; it is inert until the recipe names the platform.

**4. Workflow hardening (kept from the windows iterations).** Release-asset fetches use `curl -fsSL --retry 5 --retry-all-errors` (a transient flake fails loudly, never a silent error page the sha pin then rejects). The wrong-line refusal gate now names the **installed** payload version — the recipe's version and the registry's published version legitimately differ between a version-bump PR and its publish, and with no pin the emptied config resolves nothing at all (dispatch dies at version resolution before the runtime constraint is consulted).

**Tools pin: kept at v2.6.0** (serves all windows tool assets and the `.dll` facet install path already; v2.8.x's dll signature verification is not needed here).

# Verification

- Local (macOS arm64, against the live v0.2.0 release): `tools/stage_runtime` stages the 3.14.7 (+jit) shards with sidecar ↔ bytes ↔ shard digest assertions; `tools/gen_closure` → `closure/3.34.1-aarch64-macos.txt` (18 wheels, cp314 native members); full local leg `tools/build` + `tools/boot_smoke` → `tebako check` version + render-txt PASS, spec-17 dispatch prints `xml2rfc 3.34.1`.
- `ruby -c tools/pins.rb`, `bash -n` on all four shell tools, YAML parse of recipe + manifest + workflow, `py_compile` of the stub: clean.
- CI: the six POSIX legs + the wrong-line gate are the proof. The windows leg returns as its own PR once the factory mount tier ships.
